# 撮合引擎指南

## 🎯 什么是撮合引擎？

想象一下你在菜市场买菜：
- 你想买白菜，愿意出5元/斤
- 老板卖白菜，想要6元/斤  
- 你们讨价还价，最终5.5元/斤成交

**撮合引擎就是这个"讨价还价"的电子化系统**，专门用于数字货币、股票等金融产品的交易。它的作用是：
- 📝 收集买家和卖家的订单
- 🔍 找到价格合适的买卖双方
- ✅ 自动撮合成交
- 📊 更新市场价格和深度信息

---

## 🏗️ 系统整体架构解析

### 核心理念：分层设计
我们的撮合引擎采用了**分层架构**，就像盖房子一样，每一层都有自己的职责：

```
🏠 应用层 (客户端/API)
    ⬇️
🚪 接入层 (RabbitMQ消息队列)
    ⬇️  
🔄 业务层 (撮合引擎核心)
    ⬇️
💾 数据层 (Redis + MySQL)
```

### 🧩 核心模块详解

#### 1. **外部系统层**
- **客户端/API**: 用户提交买卖订单的入口
- **RabbitMQ**: 消息队列，确保订单不丢失
- **Redis**: 缓存，存储实时行情数据
- **MySQL**: 数据库，永久保存交易记录
- **Apollo**: 配置中心，统一管理系统配置

#### 2. **数据拉取层**
- **Puller (拉取器)**: 从消息队列中获取订单
- **Validate (验证模块)**: 检查订单是否合法

#### 3. **撮合核心层** ⭐ (最重要)
- **Match (撮合引擎)**: 大脑，负责匹配买卖订单
- **OrderBook (订单簿)**: 存储所有未成交订单的数据结构
- **Order (订单)**: 单个订单的数据模型

#### 4. **市场数据层**
- **Market (市场模块)**: 生成市场深度信息
- **L2Quote (L2行情)**: 生成实时行情数据
- **Depth (深度数据)**: 显示买卖盘口信息

#### 5. **数据处理层**
- **Persistence (持久化)**: 保存交易数据到数据库
- **Snapshotter (快照)**: 定期保存订单簿状态
- **Statistics (统计)**: 统计系统性能指标

## 💱 订单撮合主流程详解

当用户提交一个订单时，系统是如何处理的？让我们跟随一个订单的"人生轨迹"：

### 🎬 场景设定
假设用户A想要买入1个BTC，出价50000 USDT

### 📋 完整流程

#### 1. **订单提交** 
```
用户A → API → RabbitMQ消息队列
```
- 用户通过APP或网页提交买单
- 订单信息被封装成消息发送到队列

#### 2. **订单拉取**
```
RabbitMQ → Puller拉取器
```
- Puller组件从队列中获取订单消息
- 确保订单不会丢失

#### 3. **订单验证**
```
Puller → Validator验证器
```
验证内容包括：
- ✅ 用户余额是否足够
- ✅ 订单格式是否正确  
- ✅ 价格和数量是否合理

#### 4. **进入撮合引擎**
```
Validator → Matcher撮合器
```
- 如果验证通过，订单进入撮合引擎
- 如果验证失败，返回错误信息

#### 5. **查找对手方**
```
Matcher → OrderBook订单簿
```
撮合器在订单簿中寻找：
- 🔍 卖出价格 ≤ 50000 USDT的卖单
- 📊 按价格优先、时间优先排序

#### 6A. **找到匹配订单的情况**
如果找到了合适的卖单（比如49999 USDT/BTC）：

```
6. OrderBook → Matcher (返回匹配订单)
7. Matcher → Matcher (执行撮合逻辑)
8. Matcher → OrderBook (更新订单簿)
9. Matcher → L2Quote (生成成交数据)
10. L2Quote → Redis (更新行情缓存)
11. Matcher → MySQL (持久化成交记录)
12. Matcher → RabbitMQ (发布成交结果)
```

**成交细节：**
- 💰 成交价格：49999 USDT (取卖方价格)
- 📊 买方获得：1 BTC
- 📊 卖方获得：49999 USDT
- 📈 市场最新价格更新为：49999 USDT

#### 6B. **未找到匹配订单的情况**
如果没有找到合适的卖单：

```
6. Matcher → OrderBook (挂单到订单簿)
7. Matcher → L2Quote (更新深度数据)  
8. L2Quote → Redis (更新行情缓存)
```

**挂单结果：**
- 📋 订单进入买方订单簿等待
- 📊 市场深度信息更新
- ⏰ 等待有人以≤50000价格卖出

## 🧠 撮合引擎内部流程详解

撮合引擎是整个系统的"大脑"，让我们看看它是如何思考的：

### 🎯 订单类型判断

当订单进入撮合引擎时，首先要判断订单类型：

#### 1. **限价单 (Limit Order)**
- 📝 指定价格和数量
- 📊 例：买入1 BTC，价格50000 USDT
- 🎯 只能以指定价格或更好价格成交

#### 2. **市价单 (Market Order)**  
- 🚀 立即成交，不指定价格
- 📊 例：买入1 BTC，按当前市场价
- ⚡ 优先成交，价格由市场决定

#### 3. **取消单 (Cancel Order)**
- ❌ 撤销之前提交的订单
- 📊 例：取消订单ID为12345的买单
- 🗑️ 从订单簿中移除

### 🔍 价格匹配逻辑

#### 限价单处理流程：
```
限价单 → 价格匹配检查
    ├─ 有匹配 → 执行成交
    └─ 无匹配 → 加入订单簿
```

**匹配规则：**
- 买单价格 ≥ 卖单价格 → 可以成交
- 买单价格 < 卖单价格 → 无法成交，挂单等待

#### 市价单处理流程：
```
市价单 → 直接撮合 → 执行成交
```

**撮合规则：**
- 🥇 优先匹配最优价格的订单
- ⏰ 相同价格按时间优先
- 🔄 可能与多个订单成交

### ⚙️ 成交后的处理

不管是什么类型的订单成交，都要执行以下步骤：

1. **📚 更新订单簿**: 移除或修改相关订单
2. **📊 更新深度数据**: 刷新买卖盘信息  
3. **📢 发布结果**: 通知相关系统和用户
4. **📸 检查快照**: 判断是否需要保存订单簿状态

### 🔄 完成处理

最终所有操作完成，等待下一个订单的到来。

## 📊 数据结构关系详解

### 🏗️ 核心数据结构

#### 1. **Order (订单)**
想象成一张"购物清单"：
```go
Order {
    SeqId: 序列号,          // 全局唯一ID
    UserId: 用户ID,         // 谁下的单
    OrderId: 订单ID,        // 订单编号
    BuyOrSell: 买入/卖出,   // 操作类型
    Type: 订单类型,         // 限价/市价/取消
    State: 订单状态,        // 已提交/部分成交/已成交等
    Price: 价格,           // 期望价格
    UnfilledAmount: 未成交数量,    // 还有多少没成交
    AccfilledAmount: 已成交数量,   // 已经成交了多少
    CreateAt: 创建时间      // 什么时候下的单
}
```

#### 2. **OrderBook (订单簿)**
想象成两个排队队列：
```go
OrderBook {
    Symbol: 交易对,         // 比如"BTC/USDT"
    FromId: 起始ID,         // 从哪个订单开始
    cache: 订单缓存,        // 快速查找订单
    BuySet: 买单队列,       // 所有买单，价格从高到低排列
    SellSet: 卖单队列       // 所有卖单，价格从低到高排列
}
```

**排序规则：**
- 🟢 买单：价格高的在前面（愿意出高价的优先）
- 🔴 卖单：价格低的在前面（便宜货优先卖出）
- ⏰ 同价格：时间早的在前面

#### 3. **Trade (成交记录)**
想象成"交易小票"：
```go
Trade {
    TradeId: 成交ID,           // 成交记录编号
    Price: 成交价格,           // 实际成交价格
    Amount: 成交数量,          // 成交了多少
    TakerOrderId: 主动方订单ID, // 谁主动发起的成交
    MakerOrderId: 被动方订单ID, // 谁的单子被吃掉了
    Timestamp: 成交时间        // 什么时候成交的
}
```

#### 4. **DepthLevel (深度层级)**
想象成"菜市场价格牌"：
```go
DepthLevel {
    Price: 价格,              // 价格档位
    Amount: 总数量,           // 这个价格有多少货
    OrderCount: 订单数量      // 多少个人在这个价格挂单
}
```

#### 5. **Snapshot (快照)**
想象成"系统备份"：
```go
Snapshot {
    SnapshotId: 快照ID,       // 备份编号
    Symbol: 交易对,           // 哪个交易对的备份
    Timestamp: 备份时间,      // 什么时候备份的
    Data: 订单簿数据          // 完整的订单簿状态
}
```

### 🔗 数据关系

```
订单簿 包含→ 多个订单
成交结果 包含→ 多个成交记录  
L2行情 包含→ 多个深度层级
快照 保存→ 订单簿状态
```

## 🛡️ 系统设计亮点

### 1. **高性能设计**
- **红黑树存储**: OrderBook使用红黑树，插入和查找都是O(log n)复杂度
- **内存缓存**: 热点数据存储在Redis中，访问速度极快
- **异步处理**: 使用消息队列实现异步处理，提高吞吐量

### 2. **高可靠性**
- **快照机制**: 定期保存订单簿状态，系统重启时可以恢复
- **持久化存储**: 所有成交记录永久保存在MySQL中
- **消息队列**: 订单通过消息队列传输，确保不丢失

### 3. **可扩展性**
- **模块化设计**: 各个组件职责单一，易于维护和扩展
- **多交易对支持**: 每个交易对独立运行，互不影响
- **配置中心**: 使用Apollo统一管理配置，支持动态更新

### 4. **实时性**
- **L2行情**: 提供毫秒级的行情数据更新
- **深度数据**: 实时更新买卖盘信息
- **成交推送**: 成交结果立即推送给相关用户

## 🎯 关键概念解释

### 💰 什么是"撮合"？
- **撮合** = 自动匹配买卖双方
- 就像媒人介绍对象，找到条件合适的买家和卖家
- 系统自动完成，无需人工干预

### 📚 什么是"订单簿"？
- **订单簿** = 所有未成交订单的集合
- 就像餐厅的点菜单，记录了所有顾客的需求
- 买单和卖单分别排队，等待匹配

### 📊 什么是"市场深度"？
- **市场深度** = 各个价位的挂单情况
- 告诉你：什么价格有多少货，什么价格有多少需求
- 就像看菜市场的价格表，了解市场供需情况

### ⚡ 什么是"L2行情"？
- **L2行情** = Level 2实时行情数据
- 包括：最新价格、成交量、买卖盘深度等
- 比基础行情更详细，交易员常用的专业数据

### 📸 什么是"快照"？
- **快照** = 某个时刻的完整系统状态
- 就像给订单簿拍照片，记录当时的所有订单
- 用于系统恢复和数据备份

## 🚀 实际运行示例

让我们看一个完整的交易示例：

### 📝 初始状态
```
BTC/USDT 订单簿：
买单 (价格从高到低):
  50000 USDT: 0.5 BTC (用户A)
  49999 USDT: 1.0 BTC (用户B)
  49998 USDT: 0.3 BTC (用户C)

卖单 (价格从低到高):
  50001 USDT: 0.8 BTC (用户D)  
  50002 USDT: 1.2 BTC (用户E)
  50003 USDT: 0.6 BTC (用户F)
```

### 📈 新订单到来
用户G提交市价买单：买入1.5 BTC

### 🔄 撮合过程

#### 第1步：匹配最便宜的卖单
- 找到最便宜的卖单：50001 USDT, 0.8 BTC (用户D)
- 成交：0.8 BTC × 50001 USDT = 40000.8 USDT
- 用户G还需要：1.5 - 0.8 = 0.7 BTC

#### 第2步：匹配下一个卖单  
- 找到次便宜的卖单：50002 USDT, 1.2 BTC (用户E)
- 成交：0.7 BTC × 50002 USDT = 35001.4 USDT
- 用户G订单完全成交
- 用户E剩余：1.2 - 0.7 = 0.5 BTC

### 📊 最终状态
```
成交记录：
- 成交1：0.8 BTC @ 50001 USDT (买方:用户G, 卖方:用户D)
- 成交2：0.7 BTC @ 50002 USDT (买方:用户G, 卖方:用户E)

更新后的订单簿：
买单 (价格从高到低):
  50000 USDT: 0.5 BTC (用户A)
  49999 USDT: 1.0 BTC (用户B)  
  49998 USDT: 0.3 BTC (用户C)

卖单 (价格从低到高):
  50002 USDT: 0.5 BTC (用户E，剩余)
  50003 USDT: 0.6 BTC (用户F)

市场数据更新：
- 最新价格：50002 USDT
- 24小时成交量：+1.5 BTC
- 买一价：50000 USDT
- 卖一价：50002 USDT
```

## 🎓 总结

撮合引擎是一个**高度复杂但逻辑清晰**的金融交易系统：

### 🔑 核心要点
1. **分层架构**: 每层都有明确的职责
2. **异步处理**: 通过消息队列实现高并发
3. **数据结构**: 红黑树保证高性能的订单匹配
4. **实时性**: 毫秒级的行情更新和成交处理
5. **可靠性**: 多重备份和恢复机制

### 💡 设计精髓
- **简单**: 每个模块职责单一，易于理解
- **高效**: 优化的数据结构和算法
- **稳定**: 完善的错误处理和恢复机制  
- **灵活**: 支持多种订单类型和交易对
